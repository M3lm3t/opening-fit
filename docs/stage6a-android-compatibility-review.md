### Release blocker 1: misleading v4 methodology

The old `openingFitScoreTransparency.js` only recognises health v2/v3 and coverage v2/v3. With v4, it selects the legacy path. The exact bundled Evidence disclosure says:

> This legacy score mixed repertoire stability, results, evidence and weakness signals.

and:

> Component data is unavailable for this report, so OpeningFit is not inventing a breakdown.

The payload actually supplies all four v4 health components with unchanged weights 35/25/25/15. Its score remains 83, so this is a false methodology explanation and omitted breakdown, not evidence that the numerical headline was recalculated incorrectly. Screenshot: `v7-evidence.png`; full text is in `bundle-results.json`.

### Release blocker 2: unsupported progress/improvement claims

The old snapshot compatibility guard does not inspect generation versions. With a synthetic saved v3 score of 20 and current v4 score 82.68, it reports an improvement of 62.68 and accepts the reports as comparable. The old returning-progress helper rounds and reports 20 → 83, delta +63. These are deliberately synthetic comparison fixtures, not claims about real user progress. The source tests execute the submitted source's actual comparison functions.

Backend `comparisonEligibility: false` is insufficient: these old local consumers independently compute comparisons. The Stage 6A web guard fixes the current frontend but is absent from the immutable submitted bundle.

## Smallest safe solution

**For this release, hold Stage 6A deployment.** This avoids sending the corrected generation to a client proven to misinterpret it. Do not label v4 calculations as v3.

For a subsequent authorised client update, carry the small version-aware presentation and comparison changes into Android's web bundle: recognise v4's supplied components; preserve old stored score contracts; block incompatible generations in all local comparison consumers; give absent/unrecognised methodologies an explicit unavailable/unknown explanation instead of assuming the legacy formula. Retest these fixtures, then build/submit a new Android version only with separate authorisation. This review did not perform those changes or builds.

A backend-only compatibility bridge is not presently a proven smaller solution. The submitted `importClient.js` sends no report-capability/client-version marker, and saved reports can cross clients. Simply suppressing backend comparison output or routing by user agent cannot prevent old local comparison code from making claims. Any alternative must account for both generation and saved-report reads; no such bridge was implemented here.

## Review of the 18-file patch

- No unrelated application, authentication, billing, schema, RLS, mission persistence or Android changes found in the intended patch. Backend caller edits are limited to removing the unsafe name-level metric merges in both imports.
- Health component definitions were AST-compared with HEAD and are identical; weights and thresholds remain unchanged. Generation versions are genuinely new: decision v7 (structural schema remains 6), health v4, suitability v2 and auxiliary metrics v2.
- The altered unknown-result denominators/confidence inputs and membership exclusions are intentional evidence-integrity changes, not new health weights. Optional identity/trait-status fields are additive.
- Calls to decision generation/application are on the two import-build paths and demo generation. The patch introduces no saved-report read migration or persistence rewrite. Snapshot tests preserve stored score contracts; input-mutation checks passed.
- The new comparison helper deliberately gates crossing v4, rather than solving arbitrary unknown/future-version comparison policy. It is not a universal capability negotiation mechanism.
- The earlier statement that mixed-generation comparisons are blocked applies to the patched web code/backend, **not to the submitted Android bundle**. This review establishes that limitation concretely.
- `git diff --check` and reverse patch applicability checks pass. The patch SHA-256 remains `4d6e43db5886ec44e1dfc92ea12881341443be17182d8c1865dcf4af9f8e36d1`.
- All 84 protected baseline hashes still match, including the six unrelated tracked changes. No broad suite/build was repeated; the previous 428 backend / 734 frontend / lint / build results remain valid because production code was not changed in this review.

**Final recommendation: the Stage 6A patch remains locally reviewable, but is not safe to release to the recorded Android 1.0.18(21) client.**
